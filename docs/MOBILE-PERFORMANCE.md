# 모바일 렌더링 진단 · 2026-10-20

사용자가 iPhone 15 Pro의 모바일 Edge·Safari에서 버벅임을 보고했습니다. PC는 정상이라는 후속 요구에 따라 **렌더링 비용 절감은 모바일에만 적용**합니다. 이 문서의 Chromium/SwiftShader 측정은 iPhone·Safari의 성능 측정이 아닙니다.

## 클라우드에서 확인한 병목

1. **화면 밖 수목도 제출됨.** 기존 수관 1,200개가 10km 범위를 포함하는 단일 InstancedMesh였습니다. 프러스텀에 일부가 들어오면 모든 수관을 본 화면과 반사에 제출했습니다. 골든아워에서 총 735,583개의 삼각형 중 수관이 432,000개였습니다. 초기 분리 실험에서 수관만 숨겼을 때 프레임 간격 중앙값이 533ms에서 383ms로 줄었습니다. 이는 진단 실험이며 최종 구현은 나무를 제거하지 않습니다.
2. **모든 화질이 같은 수면 격자 사용.** 낮은 화질에서도 256×256 격자, 66,049 정점, 131,072 삼각형을 제출하고 정점마다 파도 텍스처를 읽었습니다. 초기 실험에서 수면 인덱스 간격을 두 배로 늘리자 총 삼각형이 98,304개 줄고 중앙 프레임 간격이 617ms에서 467ms로 줄었습니다.
3. **반사 해상도 설정 객체 오류.** Three.js 0.186.1에서 `ReflectorNode`는 텍스처 뷰이고, 실제 설정은 `mirror.reflector.resolutionScale`에 있습니다. 기존 `mirror.resolutionScale` 대입은 실제 타깃을 바꾸지 않았습니다. 390×844, DPR 3, 균형 화질에서 실제 메인 버퍼는 448×970, 반사 버퍼는 224×485였고 설정한 0.45 대신 0.5를 사용했습니다.

FFT와 업로드 예약을 포함하는 `river.update` CPU 중앙값은 초기 실험에서 약 1.1–1.7ms, DOM·오디오 등의 추가 갱신은 대부분 0–0.1ms였습니다. 수면 갱신 또는 CSS 배경 흐림을 끈 실험에서 일관된 개선이 없었습니다. FFT, 오디오, UI 갱신 방식, 하늘 셰이더는 이번 변경에서 유지합니다.

초기 진단 실험은 공유 클라우드의 변동성을 포함하며 반복 기준 장면의 중앙값도 533–583ms로 흔들렸습니다. 최종 비교는 별도 실행으로 구분합니다.

## 변경과 품질 범위

| 항목                             | PC                           | 모바일                             |
| -------------------------------- | ---------------------------- | ---------------------------------- |
| 수목                             | 기존 전체 인스턴스 묶음      | 2km 공간 셀별 묶음과 카메라별 컬링 |
| 나무 위치·색·개수·형상           | 기존 유지                    | 기존 유지                          |
| 수면 격자: 낮음/균형/높음        | 256 / 256 / 256              | 96 / 128 / 256                     |
| 반사 해상도 배율: 낮음/균형/높음 | 기존 실제 값 0.5 / 0.5 / 0.5 | 0.25 / 0.35 / 0.5                  |

| 반사 갱신 빈도·수면 노멀·FFT     | 기존 유지                    | 기존 유지                          |

모바일의 균형 수면은 삼각형 수를 75% 줄이지만 지수 격자 분포를 조정해 선체 옆 약 1m 간격과 16km 전체 범위를 유지합니다. 원경의 수면 변위는 더 성기며, 반사 디테일은 낮아집니다. 수면 색·노멀·태양 하이라이트·항적 계산과 매 프레임 반사는 유지합니다. 항해 중 격자나 나무 LOD를 바꾸지 않으므로 새 LOD 전환 팝핑이나 반사 갱신 지연을 도입하지 않습니다. 화질 변경 시 이전 격자는 dispose합니다.

작은 수목 셀마다 별도 버퍼를 만든 중간 버전에서는 새 셀이 보일 때 TSL 프로그램을 준비하면서 이동 중 7개의 long task가 발생했습니다(최대 583ms, SwiftShader). Three.js의 작은 인스턴스 버퍼는 WebGL2에서 객체마다 다른 이름의 UBO를 사용합니다. 최종 구현은 원래 1,200개 수목 버퍼의 용량을 유지해 기존과 같은 인스턴스 정점 속성 경로를 사용하고, 실제 draw count만 셀의 수목 수로 제한합니다.

추가 용량과 준비 비용을 제한하기 위해 500m 대신 2km 셀을 사용합니다. 모바일 셀의 바인딩과 파이프라인은 기존 로딩 단계의 `compileAsync`와 첫 반사 렌더에 포함하고, 준비 후 공간 컬링을 켭니다. PC의 준비 범위는 그대로입니다. 이 방식에는 추가 버퍼 메모리라는 절충이 있으며, 초기 로딩과 renderer가 보고한 메모리도 아래에 기록합니다. WebGPU 및 다른 드라이버의 실제 비용은 실기기에서 확인해야 합니다.

UA/UA Client Hints와 iPadOS의 Mac 플랫폼·터치 정보를 함께 사용합니다. 화면 너비로 모바일을 선택하지 않으므로 좁은 PC 창과 Windows 터치 노트북은 PC 경로를 유지합니다. 이는 적용 범위를 구분하기 위한 장치 분류이며 해당 기기의 GPU 성능을 추정하는 기능은 아닙니다.

## 측정 조건과 결과

- 호스트: Intel Xeon Platinum 8573C, CPU 할당 4코어, RAM 33.3GiB. 물리 GPU·연결된 iPhone 없음.
- Chromium 154.0.8037.57, ANGLE Vulkan SwiftShader, 실제 백엔드 WebGL2. iPhone Safari UA·터치·DPR만 에뮬레이션했습니다.
- 프로덕션 빌드, 균형 화질, CSS 390×844, DPR 3, 실제 메인 버퍼 448×970. 전후 동일합니다.
- 반사 버퍼만 224×485에서 157×340으로 변경했습니다(픽셀 수 약 51% 감소). 수면 정점은 66,049→16,641입니다.
- 정지 위치 4개는 같은 항로 위치·시점·시간대를 사용합니다. 파도 시간은 흐르며, 별도의 시각 비교에서는 `still=1`로 고정합니다.
- 장면마다 15프레임 워밍업 후 60프레임 수집. 캡처와 타이머 쿼리는 별도 구간입니다. `snapshot`의 누적 구간 통계가 아닌 `metrics.intervalMs`를 비교합니다.

**이 결과는 소프트웨어 렌더러의 병목 조사이며 스마트폰 FPS가 아닙니다.** 공유 CPU의 스케줄링·소프트웨어 래스터화 영향이 커서 특히 p95/p99가 흔들렸습니다. 반복 실험에서도 변동이 컸으므로 아래 시간 차이를 모바일 개선율로 해석하면 안 됩니다. 렌더 해상도와 제출 삼각형 감소는 직접 확인한 비용 변화입니다.

추가 관측:

- 앱의 `ready` 시점: 9.584→9.732초. 초기 자산·셰이더 준비를 포함하는 앱 내부 시간이며, 물리 디스플레이의 첫 표시 시점이나 네트워크 환경별 로딩 목표가 아닙니다.
- resource entry의 압축 자산 합계(HTML 제외): 761,145→761,778바이트. 자산 최적화로 인한 개선은 아닙니다.
- 골든아워 `renderer.info.memory.total`: 약 37.6→55.2MB. 마지막 이동 구간은 42.0→61.4MB. 추가 수목 버퍼·바인딩 비용이 있으며 메모리 절감을 주장하지 않습니다. 이 값은 Three.js의 리소스 계수이며 실제 프로세스 RSS·드라이버 VRAM 측정이 아닙니다.
- 셰이더 프로그램은 골든아워·교량·선미에서 전후 모두 24개, 야간 26개, 다시 골든아워 이동에서 24개였습니다. 중간 버전처럼 셀 진입마다 프로그램 수가 증가하지 않았습니다.
- 각 장면에서 렌더 패스는 전후 3개입니다. 반사와 최종 출력 패스를 유지했습니다.
- CPU 구간별 분포, JS heap, DOM 작업 시간과 타이머 쿼리는 아래 JSON에 있습니다. 소프트웨어 GPU 쿼리 12개의 중앙값은 약 570→313ms지만 측정 위치가 다른 이동 종료 후의 값이므로 엄밀한 GPU 개선율로 사용하지 않습니다. 물리 GPU 시간은 미검증입니다.

집계 원본: [수정 전](performance/before-summary.json), [수정 후](performance/after-summary.json). 두 보고서의 `source`는 측정 당시 HEAD인 기준 커밋을 가리키며, 미커밋 변경을 포함한 수정 후 빌드는 `index-DHmLppxJ.js` 자산으로 구분됩니다. 원시 프레임 로그·실험 중간 버전은 Git에 포함하지 않습니다.

## 재현

```sh
npm ci --cache /workspace/.npm-cache
npm run build
npm test
npm run test:production
npm run test:mobile
npm run test:browser
PROFILE_LABEL=current npm run test:performance
```

`test:performance`는 4181 포트의 프로덕션 빌드를 사용합니다. 장면별 15프레임 워밍업 후 60프레임을 수집하며 기본 장면은 골든아워, 교량 하부, 선미 근경, 야간, 연속 항해입니다. 스크린샷과 소프트웨어 렌더 타이머 쿼리는 프레임 측정 구간 밖에서 실행합니다. `PROFILE_SAMPLES`, `PROFILE_WARMUP`, `PROFILE_CASES`, `PROFILE_QUALITY`, `PROFILE_LABEL`, `PROFILE_DIST`로 조건과 결과 폴더를 지정할 수 있습니다. `PROFILE_GPU=1`은 별도의 12회 렌더 타이머 쿼리를 추가합니다. `PROFILE_SOFTWARE=0`은 실제 GPU가 있는 호스트에서 강제 SwiftShader 옵션을 해제합니다.

전후 실행 시 수정 전 빌드를 별도 경로에 보관하고 같은 명령·브라우저·화질·뷰포트·DPR을 사용해야 합니다. GPU 작업은 병렬 실행하지 않습니다. 기준 저장소는 `5286f17`이며, 이번 조사에서 보관한 기준 빌드는 진단 훅만 추가한 버전입니다. 생성된 JSON의 자산 해시로 빌드를 구분할 수 있습니다.

기준 버전을 다시 만들 때 사용할 [진단 훅 전용 패치](performance/baseline-diagnostics.patch)를 포함했습니다. 렌더링 설정은 바꾸지 않습니다.

```sh
# 이 저장소 루트에서 실행
git worktree add --detach /tmp/han-river-before 5286f17
git -C /tmp/han-river-before apply "$PWD/docs/performance/baseline-diagnostics.patch"
(cd /tmp/han-river-before && npm ci && npm run build)
PROFILE_LABEL=before PROFILE_DIST=/tmp/han-river-before/dist npm run test:performance
PROFILE_LABEL=after npm run test:performance
```

고정 시각의 화면 비교에는 `PROFILE_STILL=1 PROFILE_SAMPLES=1 PROFILE_WARMUP=3`을 사용합니다. PC 범위를 확인할 때는 `PROFILE_DESKTOP=1`을 추가합니다. 한 프레임 캡처 실행의 시간 값은 성능 비교에 사용하지 않습니다.

`node tests/mobile-motion.mjs`는 별도 프로덕션 서버(4184 포트)에서 모바일 경로의 4배 항해를 약 10초 동안 실제 진행시키며 영상을 기록합니다. Chromium과 `ffmpeg`가 필요합니다. 캡처된 프레임의 실제 타임스탬프로 영상을 구성하며, 녹화 비용이 포함되므로 성능 측정에 사용하지 않습니다. 일반 모바일 기능 테스트는 4183 포트를 사용합니다.

`?profile=1`에서만 `window.__HAN_RIVER__.profile`과 `inspect()`가 노출됩니다. `profile.start()`/`stop()`은 최대 2,000프레임과 long task를 기록합니다. CPU 구간은 장면 준비, 수면 갱신, 기타 갱신, 렌더 제출로 나뉩니다. 텍스처 업로드를 예약하는 CPU 비용과 GPU의 실제 업로드 비용은 구분해야 하며, 업로드 비용만의 독립 측정은 포함하지 않습니다.

원시 결과·화면 캡처는 `artifacts/performance/`에 생성되며 Git에 대용량 원시 데이터를 포함하지 않습니다.

[검증 집계](performance/validation-summary.json). 정상 흐름의 콘솔·페이지 오류는 없었습니다. 의도적으로 자산 요청을 실패시키는 복구 검사도 통과했습니다. 화질 전환 시 이전 수면 격자의 dispose 이벤트를 확인했고, 최초 고화질 그림자 리소스 준비 이후 동일 설정을 반복했을 때 geometry 계수는 41개로 유지됐습니다.

첫 전체 브라우저 검사는 독립된 두 컨텍스트에서 장면을 동시에 렌더하던 단계에서 두 번째 장면의 60초 준비 제한에 걸렸습니다. 완료된 장면을 앱의 실제 visibility 핸들러로 백그라운드 처리한 뒤 전체 검사가 통과했습니다. 타임아웃·기능 assertion을 완화하지 않았습니다. 헤드리스 탭 복귀 검사는 `document.hidden`을 임시 재정의해 실제 이벤트 핸들러를 검증하며, iOS의 실제 앱 전환·복구 검증과는 구분합니다.

터치 검사에서는 이벤트 타임스탬프→핸들러 약 1,773ms, 핸들러→다음 애니메이션 콜백 약 2.9ms의 단일 표본을 얻었습니다. 이는 화질 전환 이후 수행한 소프트웨어 렌더러 기능 검사의 표본으로, 전후 입력 지연 비교나 실제 화면 반영 시간 측정이 아닙니다. 이를 터치 응답 개선의 근거로 사용하지 않습니다.

## 시각 검증과 남은 제약

모바일의 고정된 골든아워·교량 위치·선미·야간 화면을 전후 비교했습니다. 건물·수목·교량·갑판의 위치와 형상은 유지됐고, 검사한 화면에서 새 수목 누락이나 틈은 발견하지 못했습니다. 수면 반사의 작은 구조·빛 경계는 더 부드럽고 성기게 보입니다. 파도 변위의 원경 격자도 줄었으므로 모든 거리·시선에서 동일한 시각 품질을 보장하는 변경은 아닙니다. 높은 화질은 원래 수면 격자와 반사 배율을 사용합니다.

PC는 균형 화질·1440×900·DPR 1·동일 고정 골든아워 장면에서 **1,296,000개 픽셀 모두 동일**했습니다. PNG의 SHA-256도 같았습니다. [픽셀 비교 결과](performance/desktop-image-comparison.json). PC의 모든 위치·GPU·시간대를 픽셀 비교한 것은 아니며, 세 화질의 기존 격자·반사 배율 보존은 별도 단위·프로덕션 검사로 확인했습니다.

[모바일 경로의 실제 4배 항해 캡처](performance/mobile-motion.mp4)는 약 12초 동안 수집한 17개 프레임이며, 교량 접근·통과 중 표본 프레임을 확인했습니다. [기록 조건과 이동 상태](performance/mobile-motion-summary.json). 파도 시간과 배속은 기존 로직대로 진행하며 좌표를 강제로 건너뛴 표본 영상이 아닙니다. SwiftShader와 녹화 비용 때문에 프레임 간격은 느립니다. 이 영상으로 실기기의 매끄러움이나 입력 지연을 입증하지 않습니다.

추가로 강제 소프트웨어 WebGPU 스모크 검사를 실행했지만 수정 전·후 모두 초기화 중 `A valid external Instance reference no longer exists` / `Instance dropped in popErrorScope` 오류가 발생했습니다. 동일 호스트·명령에서 기준 빌드도 실패하므로 이 결과로 변경본의 WebGPU 정상 동작을 판단할 수 없습니다. 앱의 기본 WebGL2 폴백 검사와 구분하며, WebGPU 검증 성공으로 기록하지 않습니다. 재현 시 `PROFILE_BACKEND=webgpu`를 사용합니다.

검토 시 우선 확인할 항목은 실제 iPhone의 WebGPU/WebGL2 선택과 오류 여부, 지속 프레임·터치 반응, 반사 선명도, 추가 버퍼 메모리·발열입니다. 실제 기기 결과를 확보하기 전에는 모바일 30/60fps 목표 달성이나 WebGPU 회귀 없음으로 승인하지 않는 것을 권장합니다.

## 실기기 후속 확인

iPhone 15 Pro와 iPhone 14에서 실제 사용하는 iOS·Edge·Safari 버전을 기록하고 다음 절차를 수행해야 합니다.

1. 같은 버전의 HTTPS 앱에서 균형 화질을 선택하고 렌더 백엔드·`snapshot().renderMode`를 확인합니다. WebGPU와 WebGL2는 각각 지원되는 경로에서 확인합니다.
2. 최초 로딩과 워밍업 이후를 분리하고, 같은 항로·시간대·시점에서 원본과 변경본을 비교합니다. 프레임 간격 중앙값·p95·p99, 긴 프레임, 터치 응답을 기록합니다.
3. 0.5·1·4배, 선체·교량 근경, 태양 방향과 반대 방향, 야간, 화면 회전, 탭 복귀를 확인합니다. 반사 선명도·수면 반짝임·교량 경계·수목 누락도 비교합니다.
4. 저전력 모드, 화면 주사율, 기기 온도와 배터리 상태를 맞추고 10분 이상 연속 관람해 발열에 따른 성능 저하를 확인합니다.

클라우드에서 실제 iPhone, Safari/WebKit, 모바일 WebGPU, 발열, 화면 표시까지의 입력 지연, 30/60fps 목표는 검증하지 못했습니다. 이를 달성했다고 선언하지 않습니다.
